This document describes the REST API as it is built today: every endpoint, who may call it, what it takes and returns, and how the endpoints work together in each workflow. It is written from the code (the controllers and services under `backend/src/main/java/com/schoollink`).

## 1. Conventions

### 1.1 Base URL and format

- Every endpoint is under `/api/v1`. In development the server listens on `http://localhost:8080`.
- Requests and responses are JSON, except the two file uploads (multipart) and the Twilio webhook (form fields).
- Dates are ISO (`2026-11-12`), times of day are `HH:mm` or `HH:mm:ss`, instants are ISO UTC (`2026-11-12T07:40:00Z`).
- Ids are UUIDs.

### 1.2 Authentication

- Send the access token on every call: `Authorization: Bearer <accessToken>`.
- The access token is a JWT that lasts **15 minutes**. The refresh token lasts **30 days** (NFR-7).
- A refresh token is single use. `POST /auth/refresh` returns a new pair; reusing an old refresh token revokes the session.
- These endpoints need no token: `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/schools`, `POST /auth/parent/sign-in`, `POST /auth/parent/sign-in/verify`, `POST /webhooks/sms/delivery`, and `/actuator/health`.

### 1.3 Roles and scope

There are seven roles: `ADMIN`, `TEACHER`, `ASSISTANT_DM`, `DM`, `COUNSELLOR`, `PARENT`, `RESEARCHER`. One account can hold several.

The school and the scope always come from the token, never from the request (NFR-8):

| Role | Scope |
| --- | --- |
| Admin | The whole school |
| Teacher | The classes they teach |
| DM, assistant DM | The classes of their blocks (D5) |
| Counsellor | The whole school, for reading |
| Parent | Their own children (from the guardian links of the account) |

Two answers follow from this:

- **403** when the role may not call the endpoint at all.
- **404** when the record exists but is outside the caller's school or scope. It looks as if it did not exist (D17).

### 1.4 Errors

Every error has one shape:

```json
{ "code": "auth.invalid_otp", "message": "Ce code de vérification est incorrect ou a expiré.", "field": "otp", "details": [] }
```

- `code` is stable; clients test it.
- `message` is written in the user's language (NFR-12). The language comes from the account, or from `Accept-Language` before sign-in.
- `field` names the field at fault, when there is one. `details` lists several field errors of one request.

| Status | Meaning | Typical codes |
| --- | --- | --- |
| 400 | The request is wrong | `validation.*`, `request.malformed`, `auth.invalid_otp` |
| 401 | No valid token | |
| 403 | The role may not do this | `forbidden` |
| 404 | Unknown, or outside the caller's school or scope | `not_found` |
| 409 | Conflicts with what is stored | e.g. a second session for the same class and period |
| 429 | Too many requests; `Retry-After` gives the wait in seconds | `rate_limited` |
| 503 | A provider failed | `auth.otp_not_sent` |

### 1.5 Idempotent writes

The offline screens send records that may be sent twice on a weak network. Their endpoints are idempotent on an id generated by the device (BR-6, NFR-3):

- `PUT /sessions/{id}` and `PUT /lateness/{id}` answer **201** the first time and **200** on a replay of the same content.
- The same id with different content is refused: a stored record never changes.
- `POST /messages` and `POST /announcements` take an `id` in the body and behave the same way.

### 1.6 Rate limits (NFR-7)

| What | Limit |
| --- | --- |
| Login requests per IP address | 30 per minute |
| Failed logins per source | 5 per 15 minutes |
| Failed logins per login, all addresses | 20 per hour |
| Wrong current passwords when changing a password | 5 per 15 minutes |
| Parent sign-in requests per IP address | 10 per 15 minutes |
| Parent code verifications per IP address | 30 per 15 minutes |
| SMS codes per parent | 3 per hour and 5 per day |
| Wrong tries per SMS code | 5 |

### 1.7 Privacy and audit

- Phone numbers travel in request bodies only, never in a URL, and are never logged (NFR-9).
- Every create, edit, cancellation, justification, decision and message writes a row to the append-only `audit_log` (NFR-11). Plain reads are not audited.

## 2. Workflows

Each workflow lists the calls in order and what the server does at each step.

### 2.1 Staff sign-in and session

Staff sign in with a password. The admin created the account and gave a temporary password (UC-A2, D18).

1. `GET /auth/schools` lists the schools for the picker (D16).
2. `POST /auth/login` with `{schoolId, login, password}`. `login` is the phone or the email. The answer holds the token pair and the user (`roles`, `language`, `passwordChangeRequired`).
3. If `passwordChangeRequired` is true, the app sends the user to `POST /me/password` before anything else. It returns a fresh token pair.
4. On start-up the app calls `GET /me` to confirm who is signed in.
5. When a call answers 401, the client calls `POST /auth/refresh` once and replays the call. The mobile interceptor shares one refresh between calls that fail together.
6. `POST /auth/logout` with the refresh token ends the session on the server.

### 2.2 Parent sign-in by SMS code (UC-P1, D24)

Parents have no password. The phone number the school holds is their identity.

1. `GET /auth/schools`, then `POST /auth/parent/sign-in` with `{schoolId, phone}`.
2. The server answers `{activationId, expiresAt}` **whether or not it knows the number**, so nobody can learn which numbers are registered (NFR-7).
   - If the number is a guardian's (or a parent-only account's) in that school, it stores a hashed 6-digit code valid for 10 minutes and sends it by SMS, straight to the provider.
   - Otherwise it sends nothing, and step 3 can never succeed.
   - A number that belongs to a staff account gets no code: staff use their password (D21).
3. `POST /auth/parent/sign-in/verify` with `{activationId, otp}`.
   - The first time, the server creates the parent account and links it to the guardian's children.
   - It returns the token pair. From here the parent's session works like a staff session (refresh, logout).
4. Asking for a new code makes the previous one stop working. The limits are in section 1.6; when one is reached the answer is 429 and no SMS is sent.

In development there is no SMS gateway: the code is written to the server log (`SMS (not delivered, dev): …`).

### 2.3 Roll call (UC-T1, UC-T2, UC-T3)

1. **Prepare, online:** the teacher's app calls `GET /me/classes` (their classes with the students) and `GET /me/sessions` (today's expected sessions and which are recorded). It keeps both on the phone.
2. **Record, offline:** the teacher marks the absentees and confirms twice (BR-3). The app saves the session in its local database with a new UUID.
3. **Sync:** the queue sends `PUT /sessions/{id}` with `{classId, date, periodId, confirmedAt, absentStudentIds}`.
4. **Server, one transaction:**
   - checks the teacher teaches that class (403 otherwise);
   - stores the session, locked from the start (BR-4), with one record per student of the class: present unless listed absent (BR-2, BR-5);
   - never refuses a roll because the phone's clock or class list is wrong (D42): a `confirmedAt` ahead of the server by more than 5 minutes, or before the session's date, is replaced by the server's time; an absentee who is not in the class any more is left out;
   - refuses a second session for the same class, date and period under another id (409, BR-1);
   - writes the parents' notifications to the outbox and the audit row.
5. **After the commit:** the detection rules run for the absent students (section 2.7), and the dispatcher sends the notifications (section 2.5).

A locked session is never edited. A mistake is corrected by the DM (section 2.6).

### 2.4 Lateness at the gate (UC-AD1, UC-AD2)

1. **Prepare:** `GET /lateness/students` with no `q` returns every student of the assistant DM's scope, for the offline copy. With `q` it searches by name or matricule.
2. **Record, offline:** the assistant DM picks a student; the app stores a lateness with a new UUID and the arrival time.
3. **Sync:** `PUT /lateness/{id}` with `{studentId, date, arrivalTime, recordedAt}`.
4. **Server:** checks the student is in scope, stores the record, refuses a second live lateness for the same student and day under another id (409), writes the outbox and audit rows. A wrong clock on the phone does not lose the record (D42): an arrival more than 5 minutes ahead of the server becomes the time the server received it, and a `recordedAt` ahead of the server or before the arrival becomes the server's time.
5. `GET /lateness?date=` lists the day's lateness with the school's start time.

Lateness and attendance are separate records. Neither reads or changes the other (BR-8, BR-9).

### 2.5 From a record to the parent (BR-20 to BR-25)

Nothing is sent inside a request. Everything goes through the `notification_outbox` table.

1. **Write:** in the transaction that stores an absence or a lateness, the notification module writes, for each guardian of the student:
   - a **push** row (status `QUEUED`) if the guardian has the app;
   - an **SMS** row (status `HELD`) that waits for the daily digest.
2. **Push:** the dispatcher runs every 5 seconds, claims up to 50 queued rows and sends them through Firebase. A failure is retried after 30 seconds, 2 minutes and 10 minutes (4 attempts in all), then the row is `FAILED`.
3. **Inbox:** the parent's app shows the same events with `GET /me/notifications`. Opening one calls `POST /notifications/{id}/opened`, which records the open receipt (BR-24).
4. **Digest:** at each of the school's digest times (set by the DM, section 2.9), the held SMS of each guardian, student and day become one SMS. An event whose push the guardian already opened is skipped (D33).
5. **Cap:** once the school's monthly SMS cap is reached, an SMS other than a summons fails without being sent (BR-25).
6. **Delivery report:** Twilio calls `POST /webhooks/sms/delivery`; a sent SMS becomes `DELIVERED` or `FAILED`.

For a phone to receive pushes, the app registers its token with `PUT /me/device-token` at sign-in and whenever Firebase replaces it.

### 2.6 Justifying and cancelling (UC-D1, UC-D6)

Both are done by the DM in charge of the student's class.

**Justify** (the parent explained in person, BR-11):

- `POST /justifications` with a `reason` (`ILLNESS`, `FAMILY`, `SCHOOL_ACTIVITY`, `OTHER`), an optional note, and the ids of the absences and lateness it covers.
- All the records get the justification or none does: one record out of scope, cancelled or present makes the whole request fail (BR-12).
- A record already justified takes the new justification; the audit keeps the old one.

**Cancel** (the record was a mistake, BR-13 to BR-15):

- `POST /records/{id}/cancel` for an absence, `POST /lateness/{id}/cancel` for a lateness, each with a mandatory `reason`.
- The row stays in the database, marked cancelled for good, and no longer counts anywhere.
- If the parent was already told, a correction is written to the outbox in the same transaction.

### 2.7 From a risk alert to a decision (UC-D2, BR-16 to BR-19)

The rules only raise alerts. A person decides.

1. **Evaluate:** after each stored session and each lateness, and once more in a nightly run, the three rules are evaluated for the students concerned:

   | Rule | Raises an alert when | Count allowed |
   | --- | --- | --- |
   | `FULL_DAY_ABSENCE` | Absent in every timetabled period, that many days in a row | 1 to 5 |
   | `CONSECUTIVE_LATENESS` | Late on that many school days in a row | 2 to 20 |
   | `UNJUSTIFIED_ABSENCES` | That many unjustified absent periods in the current term | 1 to 200 |

2. **Raise:** when a threshold is reached, one `RiskAlert` is created for the student and rule. A student has at most one open alert per rule (BR-17).
3. **Review:** `GET /alerts` lists the open alerts of the DM's classes, with the evidence (the dates or records that triggered it). `GET /alerts?status=closed` lists the decided ones.
4. **Decide, once:** `POST /alerts/{id}/decision` with one of:

   | Decision | Needs | Effect |
   | --- | --- | --- |
   | `DISMISS` | A note | Closes the alert |
   | `SUMMON` | Optional meeting date and time | Creates a summons, sent to the parents by push and SMS (BR-23) |
   | `DISCIPLINARY` | A note; optional category and measure | Creates a disciplinary record |
   | `REFER` | Optional note | Refers the student to the counsellor |

   The decision closes the alert and keeps who decided, when and why.

The DM can also act without an alert: `POST /summons` summons a parent directly, and `POST /students/{id}/disciplinary-records` records an incident.

### 2.8 Messages to parents (UC-D4, UC-A5, D38)

A DM writes to the guardians of one student or one class of their blocks. An admin writes an announcement to one class or the whole school.

1. `GET /messages/classes` lists the classes the author may write to, with their student counts.
2. `POST /messages/preview` (or `/announcements/preview`) with the draft returns the counts before sending: recipients, how many by app, how many by SMS, how many unreachable, the SMS units, the estimated cost, and whether it would pass the monthly cap.
3. `POST /messages` (or `/announcements`) with the same draft and an `id` sends it: the message, one outbox row per guardian and the audit row are written in one transaction. Each guardian gets it once: by push with the app, or by SMS without it if the author asked for SMS.
4. `GET /messages` and `GET /announcements` list what was sent, newest first, with delivery counts (pending, sent, delivered, opened, failed). `GET /messages?studentId=` keeps one student's messages, for the student page (D41).

Messages are never edited or deleted.

### 2.9 The DM's day

| Need | Call |
| --- | --- |
| What is waiting today | `GET /alerts` and `GET /attendance/day` (periods not recorded, students absent, lateness) |
| One day, period by period | `GET /attendance/day?date=` (never a future date) |
| A student's history | `GET /students/{id}/history?from=&to=` (default: the last 90 days) |
| A student's discipline | `GET /students/{id}/disciplinary-records` |
| The full-day absence report | `GET /reports/full-day-absences/default-date`, then `GET /reports/full-day-absences?date=` |
| The letterhead for that report | `GET /school/letterhead` and `/school/letterhead/logo` |
| The scope dashboard | `GET /dashboard/scope?from=&to=` (default: the last 30 days) |
| Thresholds, start time, digest times | `GET` and `PUT /settings/thresholds` |

Notes on the full-day report (UC-D9, D36):

- A student is listed when every timetabled period of their class that day was recorded and they were absent, unjustified, in all of them.
- A class with a timetabled period never recorded lists nobody. It is named in `unrecorded`, because its full-day absences cannot be known.
- Today's report is available from 17:00 school time; before that the default date is the previous school day.
- The phone draws the PDF itself; the web prints the page under the letterhead.

### 2.10 The parent's side (UC-P2, UC-P3, UC-P5)

| Need | Call |
| --- | --- |
| My children | `GET /me/children` |
| A child's attendance and lateness | `GET /children/{id}/history?from=&to=` |
| Whom to contact about a child | `GET /me/children/{id}/contacts` (the class's teachers and the block's DMs, with phones, D39) |
| My notifications | `GET /me/notifications?before=&limit=` |
| Mark one as read | `POST /notifications/{id}/opened` |

Another family's child answers 404.

### 2.11 Setting up a school (UC-A1 to UC-A3, UC-A7)

The admin does this on the web, in this order, because each step needs the one before:

1. **Calendar:** academic year, then its terms, then the holidays of each term.
2. **Day:** the periods (number, start and end time).
3. **Structure:** the blocks, then the classes (each in a year and a block).
4. **Staff:** create each account (`POST /staff` returns a temporary password to hand over), give roles (`DM` and `ASSISTANT_DM` with a block), and give teachers their classes and subjects.
5. **Timetable:** one slot per class, weekday and period, with the teacher and the subject. The timetable decides which sessions are expected (D1).
6. **Students:** import a CSV or Excel file (see [IMPORT.md](IMPORT.md)):
   - `POST /students/import` (multipart: `academicYearId`, `file`) checks every row and stores them with their errors. Nothing reaches the student tables yet.
   - `GET /students/import/{id}` shows the preview again.
   - `POST /students/import/{id}/commit` creates the students and guardians, all or nothing, once (D19).
7. **Letterhead:** `PUT /school/letterhead` and `PUT /school/letterhead/logo`, used on the DM's report.

After that, `GET /guardians?classId=` shows the guardians of a class and whether each has an app account.

## 3. Endpoint reference

Paths are given without the `/api/v1` prefix. "Scope" means the caller's classes as defined in section 1.3.

### 3.1 Authentication and account (`auth`)

| Method and path | Who | Purpose |
| --- | --- | --- |
| `GET /auth/schools` | Public | Schools for the picker: `[{id, name}]` |
| `POST /auth/login` | Public | Staff sign-in |
| `POST /auth/parent/sign-in` | Public | Parent step 1: send an SMS code |
| `POST /auth/parent/sign-in/verify` | Public | Parent step 2: check the code, sign in |
| `POST /auth/refresh` | Public | Exchange a refresh token for a new pair |
| `POST /auth/logout` | Public | Revoke the session of a refresh token (204) |
| `GET /me` | Any signed-in user | The signed-in user |
| `POST /me/password` | Any signed-in user | Change the password; returns a new token pair |

Bodies:

| Call | Request | Response |
| --- | --- | --- |
| Login | `{schoolId?, login, password}` | `TokenResponse` |
| Parent sign-in | `{schoolId, phone}` | `{activationId, expiresAt}` |
| Verify | `{activationId, otp}` | `TokenResponse` |
| Refresh, logout | `{refreshToken}` | `TokenResponse` / none |
| Change password | `{currentPassword, newPassword}` (8 to 72 characters) | `TokenResponse` |

`TokenResponse`: `{tokenType: "Bearer", accessToken, expiresIn, refreshToken, user}`, where `user` is `{id, schoolId, roles, language, passwordChangeRequired}`.

### 3.2 Attendance (`attendance`)

| Method and path | Who | Purpose |
| --- | --- | --- |
| `GET /me/sessions?date=` | Teacher | The day's expected sessions and which are recorded |
| `PUT /sessions/{id}` | Teacher, own classes | Store a confirmed session (201, or 200 on replay) |
| `POST /records/{id}/cancel` | DM, scope | Cancel an absence recorded by mistake |

- `GET /me/sessions` returns `{date, schoolDay, sessions}`. Each session: `{classId, className, periodId, periodNumber, startTime, endTime, subject, current, recorded, sessionId, confirmedAt, absentCount}`. `date` defaults to today in the school's time zone.
- `PUT /sessions/{id}` takes `{classId, date, periodId, confirmedAt, absentStudentIds}` (at most 300 ids) and returns `{id, classId, date, periodId, confirmedAt, syncedAt, studentCount, absentStudentIds}`. The answer holds what was stored: `confirmedAt` and `absentStudentIds` can differ from the request (D42). The phone's own time is kept in `device_confirmed_at`, and the audit row lists the ids left out. A replay of the original request still returns 200.
- Cancel takes `{reason}` and returns `{id, cancelledAt, cancelledBy, reason}`.

### 3.3 Lateness (`lateness`)

| Method and path | Who | Purpose |
| --- | --- | --- |
| `GET /lateness/students?q=` | Assistant DM, DM | Students of the scope, to pick from at the gate |
| `GET /lateness?date=` | Admin (whole school), assistant DM, DM (scope) | The day's lateness |
| `PUT /lateness/{id}` | Assistant DM, scope | Store a lateness (201, or 200 on replay) |
| `POST /lateness/{id}/cancel` | DM, scope | Cancel a lateness recorded by mistake (D11) |

- Students: `[{id, matricule, firstName, lastName, classId, className}]`.
- Day: `{date, startTime, lateness}`. Each item: `{id, studentId, firstName, lastName, classId, className, arrivalTime, recordedAt, recordedBy, justified}`.
- `PUT` takes `{studentId, date, arrivalTime, recordedAt}` and returns `{id, studentId, date, arrivalTime, recordedAt, syncedAt}`. The answer holds what was stored: the two times can differ from the request (D42). The phone's own times are kept in `device_arrival_time` and `device_recorded_at`. A replay of the original request still returns 200. An arrival at or before the school's start time is still refused (`lateness.not_late`, BR-7).
- Cancel takes `{reason}`.

### 3.4 Justification (`justification`)

| Method and path | Who | Purpose |
| --- | --- | --- |
| `POST /justifications` | DM, scope | Justify one or several absences and lateness (201) |

Request: `{reason, note?, absenceIds?, latenessIds?}`. Response: `{id, reason, note, recordedAt, absenceIds, latenessIds}`.

### 3.5 Detection: alerts and settings (`detection`)

| Method and path | Who | Purpose |
| --- | --- | --- |
| `GET /alerts?status=open\|closed` | DM, scope | Risk alerts; `open` by default |
| `POST /alerts/{id}/decision` | DM, scope | Decide an alert, once |
| `GET /settings/thresholds` | DM | Rules, school start time, digest times |
| `PUT /settings/thresholds` | DM | Change them (one set per school) |

- An alert: `{id, studentId, firstName, lastName, matricule, classId, className, ruleType, threshold, asOf, evidence, status, raisedAt, decision, decisionNote, decidedBy, decidedAt, outcomeId}`.
- Decision request: `{decision, note?, meetingDate?, meetingTime?, category?, measure?}`. See the table in section 2.7.
- Settings: `{startTime, digestTimes, rules}`. Each rule: `{type, count, unit, window, active, min, max, updatedAt, updatedBy}`.
- Settings request: `{startTime, digestTimes (1 or 2), rules: [{type, count, active}]}`. The start time must be between 05:00 and 12:00, digest times between 06:00 and 20:00 with the second after the first, and each count within its rule's `min` and `max`, whether the rule is active or not.

### 3.6 Discipline (`discipline`)

| Method and path | Who | Purpose |
| --- | --- | --- |
| `GET /students/{id}/disciplinary-records` | Admin; DM, scope | A student's disciplinary records |
| `POST /students/{id}/disciplinary-records` | DM, scope | Record an incident (201) |
| `POST /disciplinary-records/{id}/close` | DM, scope | Close a record, with an optional note |
| `POST /disciplinary-records/{id}/cancel` | DM, scope | Cancel a record, with a reason (204) |
| `POST /summons` | DM, scope | Summon a student's parents (201) |

- Incident request: `{category, measure, occurredOn, description}`.
  - `category`: `BEHAVIOUR`, `INSOLENCE`, `FIGHT`, `ABSENTEEISM`, `CHEATING`, `DRESS`, `PHONE`, `DAMAGE`, `OTHER`.
  - `measure`: `NONE`, `WARNING`, `DETENTION`, `SUSPENSION`, `OTHER`.
- A record: `{id, studentId, alertId, category, measure, occurredOn, description, status, closeNote, recordedByName, recordedAt, closedAt}`.
- Summons request: `{studentId, meetingDate?, meetingTime?, reason?}`. Response: `{id, studentId, alertId, meetingDate, meetingTime, reason, sentBy, sentAt}`. A summons goes by push and by SMS at once, outside the digest and the monthly cap (BR-23).

### 3.7 Notifications and messages (`notification`)

| Method and path | Who | Purpose |
| --- | --- | --- |
| `PUT /me/device-token` | Teacher, assistant DM, DM, counsellor, parent | Register the phone's push token (204) |
| `GET /me/notifications?before=&limit=` | Parent | The inbox, newest first |
| `POST /notifications/{id}/opened` | Parent | Open receipt (204) |
| `GET /messages/classes` | DM, admin | Classes the author may write to |
| `POST /messages/preview` | DM | Counts and SMS cost of a draft |
| `POST /messages` | DM | Send a message (201, or 200 if this id was already sent) |
| `GET /messages?limit=&studentId=` | DM | Messages the DM sent |
| `POST /announcements/preview` | Admin | Counts and SMS cost of a draft |
| `POST /announcements` | Admin | Send an announcement |
| `GET /announcements?limit=` | Admin | The school's announcements |
| `POST /webhooks/sms/delivery` | Twilio (signed) | Delivery report of an SMS (204) |

- Device token request: `{token, platform: "ANDROID"}`.
- Inbox entry: `{id, eventType, studentId, title, body, createdAt, openedAt}`. `before` is the id of the last entry already shown.
- Draft: `{id, studentId?, classId?, body, sms?, plainSms?}`. A DM gives a student or a class; an admin gives a class or neither (the whole school).
- Preview: `{recipients, byApp, bySms, unreached, smsUnits, smsUnicode, smsLeft, estimatedCost, overCap, smsSample}`.
- Sent message: `{id, kind, audience, studentId, studentName, classId, className, body, sms, authorName, createdAt, delivery}`, with `delivery`: `{recipients, pending, sent, delivered, opened, failed}`.
- The webhook is trusted only when its `X-Twilio-Signature` matches and it names the school's Twilio account; otherwise 403.

### 3.8 People (`people`)

**Staff (UC-A2)**

| Method and path | Who | Purpose |
| --- | --- | --- |
| `GET /staff` | Admin (full); counsellor (whole school, names only); teacher, assistant DM, DM (colleagues of their classes, names only) | List staff |
| `GET /staff/{id}` | Admin | One staff member |
| `POST /staff` | Admin | Create an account (201); returns the temporary password |
| `PUT /staff/{id}` | Admin | Change name, phone, email, language |
| `PUT /staff/{id}/status` | Admin | `ACTIVE` or `DISABLED` |
| `POST /staff/{id}/password-reset` | Admin | New temporary password |
| `POST /staff/{id}/roles` | Admin | Add a role (201) |
| `DELETE /staff/{id}/roles/{roleId}` | Admin | Remove a role (204) |
| `POST /staff/{id}/teaching` | Admin | Add a class and subject taught (201) |
| `DELETE /staff/{id}/teaching/{teachingId}` | Admin | Remove it (204) |

- Staff request: `{firstName, lastName, phone?, email?, language: "FR"|"EN"}`.
- Full view: `{id, firstName, lastName, phone, email, language, status, passwordChangeRequired, roles: [{id, role, blockId}], teaching: [{id, classId, subject}]}`.
- Summary for non-admins: `{id, firstName, lastName, roles}`.

## 4. Background jobs

These run inside the same application; there is no separate service or broker.

| Job | When | What it does |
| --- | --- | --- |
| Outbox dispatcher | Every 5 seconds | Sends queued pushes and SMS, in batches of 50, with retries (section 2.5). A row left "sending" for over 2 minutes is taken again, so a notification may go twice but never zero times. |
| SMS digest | Checked every minute | At each school's digest times, groups the held SMS into one per guardian, student and day. A run missed while the server was down happens when it comes back. |
| Detection after a record | After each session or lateness commits | Evaluates the rules for the students concerned, on its own small executor. A failure is logged and left to the nightly run. |
| Nightly detection | Checked hourly, runs at 20:00 school time | Evaluates the rules again for the day, so nothing is missed. |
